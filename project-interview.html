Eval-uate-Me

一个用于 LLM Agent 评测、回归门禁和评测器自检的 Python 框架。本文重点不是罗列功能，而是解释：为什么要这样设计、如何做技术取舍、面试官追问时怎么回答。

Python ≥ 3.11Plugin-based零运行时依赖CLI + CI
测试 Agent，也测试测试方法核心设计目标：让 Agent 质量从“主观感觉”变成可重复、可比较、可追溯的工程结果。
为什么做设计推导架构流程模块边界面试拷打运行方式

一、先讲清楚为什么做

传统单元测试通常比较固定输入和固定输出，但 LLM Agent 的输出可能有多种正确表达，还可能调用工具、维护多轮上下文、遭遇提示注入。只用字符串断言，会漏掉大量真实问题。

01

输出不完全确定

同一个问题可能有多种合理答案，必须从格式、事实、约束和质量维度评分。

02

行为不只是文本

Agent 还会调用工具、读写状态、产生多轮轨迹，评测对象应该是完整行为。

03

升级后容易回归

模型、prompt、工具或数据变化都可能让通过率下降，需要 baseline 和 CI gate。

面试中的一句话：我把问题拆成三层：Agent 能不能运行、输出是否正确、评测器能不能发现错误；对应设计成 Runner、Grader 和 Meta-eval。

二、设计思路是如何推导出来的

我不是先堆技术栈，而是从“什么结果值得信任”反推架构。

1. 抽象 Target

Python 函数、HTTP 服务和有状态插件都可以成为被测对象。统一 Target 接口后，Runner 不需要知道 Agent 的实现细节。

2. 分离数据与评分

Case 只描述输入和期望约束，Grader 决定如何判分。同一数据可以复用 schema、事实、分类和 LLM Judge。

3. 保留原始证据

不只保存一个平均分，还保存输入、原始输出、逐项评分、错误原因和运行元信息，保证失败可定位。

4. 评测器也要被测

通过 mutation 故意删除字段、伪造事实或破坏工具调用，检查 grader 是否真的能把坏 Agent 判低分。

5. 先保证可复现

个人项目优先选择离线可运行、零运行时依赖、清晰插件边界；不为了“看起来大”而过早引入分布式系统。

6. 安全默认开启

对可能执行工具的目标支持进程或 Docker 隔离，并设置超时和资源限制；同时明确它不是万能安全沙箱。

关键取舍

确定性优先：能用规则判断就不用 LLM Judge。
可解释优先：保留分项结果，而不是只给总分。
演进优先：插件接口允许逐步增加模型、grader 和执行器。

暂时不做什么

暂不追求云端调度、海量数据仓库和复杂实时计算。当前目标是把单机评测闭环做扎实，再根据规模瓶颈替换存储和调度层。

三、系统架构与数据流

# 设计上的单向数据流
cases.jsonl → Runner → Target → raw output → Graders
├→ per-case result
├→ summary metrics
└→ baseline / gate decision

四、模块边界怎么解释

模块责任为什么独立
runner / execution调度用例、超时、重试、并发执行策略变化不应影响评分逻辑
targets / adapters适配函数、HTTP 和插件被测 Agent 可替换，框架保持稳定
graders / judges规则评分和 LLM Judge不同任务需要不同正确性定义
gate / baseline比较历史结果并判定回归把质量检查接入 CI，而不是人工看报告
mutation / metaeval制造坏输出并检测盲区证明测试体系本身具备区分能力
report / stats输出逐例证据、汇总指标和 HTML平均分之外还要能解释失败原因

五、面试官拷打：可以这样回答

为什么不直接写几个 pytest？

答：pytest 解决断言和测试生命周期，但这个项目还要统一接入不同 Agent、批量运行、记录轨迹、汇总指标、做 baseline 对比，并验证 grader 能不能发现故障。我不是替代 pytest，而是补上 Agent 评测的生命周期。

LLM 输出不稳定，你怎么判断对错？

答：按任务类型组合 grader：结构用 schema，事实用规则或参考字段，开放式回复才使用带 rubric 的 LLM Judge。保存分项分数和理由，并固定数据 split、模型版本，重复运行观察方差。

换模型后 baseline 还能直接比较吗？

答：不能盲比。baseline 必须绑定数据集版本、split、配置和模型元信息。模型变化后建立新的实验基线，同时保留旧基线做历史追踪；不同数据集或 split 则拒绝比较。

meta-eval 为什么有价值？

答：高分不一定代表评测有效，可能是数据太简单或 grader 太弱。故意删除答案、伪造引用后，如果分数仍然不降，就证明测试有盲区，需要补 case 或 grader。

为什么需要隔离执行？

答：Agent 可能执行工具、访问文件或消耗大量资源。进程或 Docker 隔离可以限制超时和资源，降低对宿主环境的影响。但它不是完整安全沙箱，高风险部署还需要权限、网络和密钥策略。

这个项目最大的不足是什么？

答：目前更适合单机和中小规模评测，分布式调度、长期结果存储、成本优化和 grader 一致性分析还可以加强。我的演进顺序是先补成本/延迟指标和结果存储，再根据并发瓶颈引入 worker 集群。

30 秒项目介绍：我做了一个 LLM Agent 评测框架。因为 Agent 输出非确定、工具调用复杂，传统断言容易漏掉回归。我把系统拆成统一 Target、批量 Runner、可插拔 Grader、报告和质量 Gate，并加入 mutation-based meta-eval 检查评测器盲区。重点不是调用模型，而是把 AI 质量控制工程化。

六、现场演示怎么讲

面试演示不要只打开代码，建议按“制造问题 → 运行评测 → 发现回归 → 解释设计”演示。

# 创建并检查评测项目
python3.12 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/eval_uate_me init my-eval
.venv/bin/eval_uate_me check eval.toml

# 正常评测与基线
.venv/bin/eval_uate_me run eval.toml
.venv/bin/eval_uate_me baseline promote --config eval.toml

# 修改 Agent 后检查回归
.venv/bin/eval_uate_me gate eval.toml

# 故意损坏 Agent，检查评测器是否能发现
.venv/bin/eval_uate_me meta-eval eval.toml --auto

最后的项目定位

工程能力

接口抽象、CLI、配置校验、错误处理、隔离执行和 CI 门禁。

AI 能力

Agent 评测、LLM Judge、多轮工具调用、提示注入抵抗和质量指标。

思考能力

知道如何定义正确性，也知道如何证明自己的评测方法没有失效。
